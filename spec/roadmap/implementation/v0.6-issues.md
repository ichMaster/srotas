# v0.6 — GitHub Issues

Issues for phase **v0.6 — Wikipedia + Google News collectors** (version
**v0 — Prototype**), derived from the per-phase Tasks in
[ROADMAP.md](../../ROADMAP.md) (§0.6) and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md) (§Collectors, §Item store,
§Scoring). This file is scoped to a single phase; IDs continue from the
previous phase (SROTAS-018 → **SROTAS-019…021**).

The feed draws on all three sources now. Two new collector modules —
`collectors/wikipedia.py` (REST search + the daily featured feed, no
`published_at`) and `collectors/gnews.py` (Google News RSS via feedparser,
en-US, one OR-joined request per node) — join the existing Guardian collector
in `core/pipeline.run_pass`, writing into the same `items.sqlite`; URL-PK
upsert already gives cross-source dedup for free. Exactly two new modules, no
plugin framework (MISSION §Scope boundaries is binding).

## v0.6 — Wikipedia + Google News collectors

### SROTAS-019 — `collectors/wikipedia.py` — REST search + daily featured feed

**Description:**
The second collector. `collectors/wikipedia.py` turns each node's `keywords`
into one MediaWiki REST search request (`en.wikipedia.org/w/rest.php/v1/search/page`),
OR-joined the same way as Guardian, plus a single **daily featured article**
fetch per collection run (`en.wikipedia.org/api/rest_v1/feed/featured/{Y}/{M}/{D}`,
not tied to any node). Both normalize into `Item` rows with `source="wikipedia"`
and **`published_at=None`** — Wikipedia has no publication date; the feed day
falls back to `first_seen` (ARCHITECTURE §Collectors, §Item store).

**What needs to be done:**
- `build_query(node)` — OR-join a node's keywords (same shape as
  `collectors/guardian.build_query`).
- `search(node, client)` — one request to the REST v1 search endpoint per node;
  normalize each result (`title`, `excerpt`/`description`, `key` → the article
  URL `https://en.wikipedia.org/wiki/{key}`) into an `Item`
  (`source="wikipedia"`, `published_at=None`).
- `featured(client, *, today=None)` — one request per collection run to the
  featured-feed endpoint (date injectable for deterministic tests); normalize
  the `tfa` (today's featured article) object into an `Item` the same way.
- `collect(nodes, db_path, *, client=None)` — runs `search` per node **and**
  one `featured` call, upserts everything via `core/items.py`. Reuse the shared
  `CollectSummary` shape (relocate it from `collectors/guardian.py` to a small
  shared spot — e.g. `collectors/base.py` — re-exported as
  `guardian.CollectSummary` so nothing else breaks).
- All Wikipedia HTTP is **mocked** via an injected `httpx.Client` (`MockTransport`)
  — never a live/paid call in CI.

**Dependencies:** SROTAS-006, SROTAS-002

**Expected result:**
Running the Wikipedia collector over the 14 nodes fills `items.sqlite` with
normalized, undated Wikipedia items, plus the day's featured article.

**Acceptance criteria:**
- [ ] One search request per node (OR-joined keywords), not one per keyword.
- [ ] **Unit test:** a mocked search response → normalized `Item`s
      (title/excerpt/url mapping; `published_at` is `None`).
- [ ] **Unit test:** a mocked featured-feed response → one normalized `Item`
      independent of any node's keywords.
- [ ] **Unit test:** the search query for a node is built from its keywords
      OR-joined (assert the request), against a mock — no live call.
- [ ] Ties to the phase DoD (Wikipedia items land in `items.sqlite`).

### SROTAS-020 — `collectors/gnews.py` — Google News RSS, one OR-joined request per node

**Description:**
The third collector. `collectors/gnews.py` turns each node's `keywords` into
**one OR-joined Google News RSS request per node**
(`news.google.com/rss/search?q=...&hl=en-US&gl=US&ceid=US:en`, English locale
only — same per-node budget strategy as Guardian: per-keyword would mean
~590 unauthenticated requests/day). The RSS body is fetched over an injectable
`httpx.Client` (mockable) and handed to **`feedparser`** for parsing — never
`feedparser.parse(url)` directly, which bypasses the mockable HTTP seam
(ARCHITECTURE §Collectors).

**What needs to be done:**
- `build_query(node)` — OR-join a node's keywords into the RSS `q` parameter,
  with the fixed locale params (`hl=en-US&gl=US&ceid=US:en`).
- `search(node, client)` — one GET per node; parse the response body with
  `feedparser.parse(response.content)`; normalize each entry (`title`,
  `summary`, `link`, `published_parsed` → ISO-8601 `published_at`) into an
  `Item` (`source="gnews"`).
- `collect(nodes, db_path, *, client=None)` — one request per node, upserts via
  `core/items.py`; reuse the shared `CollectSummary`.
- Add the `feedparser` dependency. All GNews HTTP is **mocked** via an injected
  `httpx.Client` — never a live/paid call in CI.

**Dependencies:** SROTAS-006, SROTAS-002

**Expected result:**
Running the GNews collector over the 14 nodes fills `items.sqlite` with
normalized, dated Google News items.

**Acceptance criteria:**
- [ ] Exactly **one** request per node (OR-joined keywords), not one per
      keyword; the fixed `hl=en-US&gl=US&ceid=US:en` locale params are present.
- [ ] **Unit test:** a mocked RSS body → normalized `Item`s (title/summary/url/
      published_at mapping) via `feedparser`, against a mock — no live call.
- [ ] **Unit test:** the request query for a node is built from its keywords
      OR-joined (assert the `q` parameter).
- [ ] Ties to the phase DoD (GNews items land in `items.sqlite`).

### SROTAS-021 — Wire both into `run_pass` + cross-source URL dedup

**Description:**
Closes the phase DoD: `core/pipeline.run_pass` now runs **all three**
collectors (Guardian, Wikipedia, GNews) into the same `items.sqlite` before the
embed → score steps. URL-PK upsert already dedups across sources for free —
this issue proves it end to end and updates `PassSummary` to report all three.

**What needs to be done:**
- Extend `core/pipeline.run_pass` to call `wikipedia.collect` and
  `gnews.collect` alongside `guardian.collect` (all three feeding the same
  `db_path`); injectable clients per collector for tests.
- `PassSummary.collected` becomes a mapping (e.g. `{"guardian": ...,
  "wikipedia": ..., "gnews": ...}`) of the shared `CollectSummary` type instead
  of a single Guardian-only field.
- No new scheduler/APScheduler work — the existing v0.4 job already calls
  `run_pass`; it now collects from three sources automatically.

**Dependencies:** SROTAS-019, SROTAS-020, SROTAS-011

**Expected result:**
One `run_pass` call collects from all three sources into `items.sqlite`,
deduplicated by URL, then embeds and scores the combined set.

**Acceptance criteria:**
- [ ] `run_pass` invokes all three collectors (mocked clients in tests) into
      the same `items.sqlite`.
- [ ] **Unit test:** two sources returning the same article URL produce a
      single row (cross-source URL dedup) — against mocks, no live call.
- [ ] **Unit test:** items from all three sources are present after one
      `run_pass` call and get embedded + scored together.
- [ ] Ties to the phase DoD (the feed shows items from all three sources;
      pytest green).
