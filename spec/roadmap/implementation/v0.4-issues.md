# v0.4 — GitHub Issues

Issues for phase **v0.4 — Web feed** (version **v0 — Prototype**), derived from
the per-phase Tasks in [ROADMAP.md](../../ROADMAP.md) (§0.4) and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md) (§Feed, §Item store, §Scoring,
§Configuration). This file is scoped to a single phase; IDs continue from the
previous phase (SROTAS-012 → **SROTAS-013…015**).

This phase makes the scored items **visible in a browser** and lets the app
**refresh itself**. It stands up `web/app.py` (FastAPI + HTMX, bound to
127.0.0.1 only) rendering the card feed — fresh days on top, score-sorted within
a day, with a clickable node-tag filter — and wires an APScheduler job inside the
process that runs the collect → embed → score pass every 4 hours. The feedback
field renders on each card but posts nowhere yet (the handler arrives in 0.5);
translation and the language toggle are **not** here (phases 0.8/0.9).

## v0.4 — Web feed

### SROTAS-013 — `web/app.py` — FastAPI+HTMX card feed (127.0.0.1), day-grouped, score-sorted

**Description:**
The web feed screen — the first thing visible in a browser. `web/app.py` is a
FastAPI app **bound to 127.0.0.1 only** (it will expose a money-spending,
model-mutating POST at 0.5); `GET /` reads the scored items from `items.sqlite`
and renders them as HTMX cards via `web/templates/`. Cards group into days
(day = `date(published_at)`, falling back to `first_seen`), fresh days on top,
and within a day sort by **descending score** (ARCHITECTURE §Feed).

**What needs to be done:**
- `core/items.py` — `read_feed(db_path)`: the scored items (`top_node` not NULL)
  with the card fields (url, source, title, summary, published_at, first_seen,
  score, top_node), highest score first.
- `web/app.py` — FastAPI app; `GET /` assembles the feed: group items by day
  (published_at date, fallback first_seen), fresh days first, score desc within a
  day; the node tag shows the `top_node`'s Ukrainian **label** (from
  `core/model.py`), the "why suggested."
- `web/templates/` — Jinja2 + HTMX: the feed screen + a card partial (title
  link, source, date, score, node tag, and a feedback text field that **renders
  but posts nowhere** — the handler is 0.5).
- Bind to **127.0.0.1** only; add `fastapi`, `uvicorn`, `jinja2` deps.

**Dependencies:** SROTAS-006, SROTAS-010

**Expected result:**
`uvicorn web.app:app` serves a browser feed of scored cards, fresh days on top
and score-sorted within a day.

**Acceptance criteria:**
- [ ] `GET /` renders one card per scored item, grouped by day (published_at,
      fallback first_seen), fresh days first, score descending within a day.
- [ ] Each card shows title link, source, date, score, node tag (the `top_node`
      label) and an **inert** feedback field.
- [ ] The app binds to **127.0.0.1** only (no external interface).
- [ ] **Unit test (FastAPI TestClient):** the feed route renders cards sorted by
      score within a day, fresh days first — against a temp `items.sqlite`
      (no paid/network call).
- [ ] Ties to the phase DoD (the feed is usable in a browser).

### SROTAS-014 — Clickable node-tag filter (`?node=`, "всі" resets)

**Description:**
Filtering lives in the cards, not a separate panel. Each card's node tag is a
clickable link that filters the feed to that node; an **"всі"** (all) link
resets. No filter-button panel, no period toggle (ARCHITECTURE §Feed).

**What needs to be done:**
- `GET /` accepts an optional `?node=<node_id>`; when present, only that node's
  items render; the "всі" link clears it.
- Each card's node tag links to `?node=<its top_node>`; an "всі" reset link is
  shown when a filter is active.

**Dependencies:** SROTAS-013

**Expected result:**
Clicking a card's node tag narrows the feed to that node; "всі" resets to the
full feed.

**Acceptance criteria:**
- [ ] `?node=<id>` narrows the feed to items whose `top_node` is that id;
      absent (or "всі") shows all.
- [ ] Each card's node tag links to its own node filter.
- [ ] **Unit test (TestClient):** the tag filter narrows the feed to one node and
      the reset shows all — against a temp DB (no paid/network call).
- [ ] Ties to the phase DoD (tag filtering works).

### SROTAS-015 — APScheduler inside the app — 4h collect→embed→score

**Description:**
The app refreshes itself. APScheduler runs **inside** the uvicorn process; every
4 hours (config interval) it runs the collect → embed → score pass
(`core/pipeline.run_pass`, from 0.3). One process, no separate worker
(ARCHITECTURE §Scoring, §Feed).

**What needs to be done:**
- Add the **collection interval** (hours, 4 default) to `config.toml` +
  `core/config.py` + `config.example.toml`.
- Register an APScheduler job at app startup that runs `pipeline.run_pass` on the
  configured interval, inside the app process; add the `apscheduler` dep.
- The pass stays **collect → embed → score** (translation is phase 0.8 — do not
  add it here).

**Dependencies:** SROTAS-013, SROTAS-011

**Expected result:**
The running app collects, embeds, and scores every 4 hours without a separate
process.

**Acceptance criteria:**
- [ ] An APScheduler job is registered at startup with the configured interval
      (4h default).
- [ ] The job runs the collect → embed → score pass (`pipeline.run_pass`).
- [ ] **Unit test:** the job is registered with the expected interval, and
      invoking it runs the pass with collection **mocked** (no paid/network call).
- [ ] Ties to the phase DoD (the scheduler collects on interval).

**Critical path:** SROTAS-013 → SROTAS-014 / SROTAS-015 (the latter two run in
parallel after the gate; SROTAS-011 from v0.3 is a prerequisite of SROTAS-015).

scheduler collects on interval; tag filtering works; pytest green.

"filter lives in the card tags" rule are honored, not newly pinned.

renders but posts nowhere — 0.5); translation and the language toggle (0.8/0.9);
Wikipedia/GNews sources (0.6). No stubs or config flags for them (MISSION §Scope
boundaries is binding).
**Mock note:** all paid APIs (Voyage embeddings, Anthropic classification) and
all collector HTTP (Guardian / Wikipedia / GNews) are **mocked** in tests —
never a paid or networked call in CI. FastAPI routes are exercised with the
TestClient; the scheduler job is tested with collection mocked.
