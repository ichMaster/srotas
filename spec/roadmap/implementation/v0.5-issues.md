# v0.5 — GitHub Issues

Issues for phase **v0.5 — Feedback loop, end to end** (version **v0 — Prototype**),
derived from the per-phase Tasks in [ROADMAP.md](../../ROADMAP.md) (§0.5) and the
contracts in [ARCHITECTURE.md](../../ARCHITECTURE.md) (§Feedback, §Memory
package, §Event journal, §Scoring, §Configuration). This file is scoped to a
single phase; IDs continue from the previous phase (SROTAS-015 →
**SROTAS-016…018**).

This phase closes the learning loop: a card's plain-text reaction is classified
by a Haiku call into `like | dislike | new_topic`, the delta lands on the card's
`top_node` in `model.yaml` (ruamel round-trip), every change is journaled with
the original text, and the feed re-scores immediately (free — embeddings
cached). `new_topic` never auto-creates a node — it queues in
`pending_topics.yaml` for manual confirmation.

## v0.5 — Feedback loop, end to end

### SROTAS-016 — `core/feedback.py` — Haiku classifier (anthropic SDK)

**Description:**
The classifier seam. One Haiku-class call via the `anthropic` SDK classifies a
card's plain-text reaction into a structured `{reaction, topic_hint}`. The
classifier receives the **card's context** — item title + `top_node` — alongside
the user's text: "more like this" is unclassifiable without knowing what "this"
is (ARCHITECTURE §Feedback). Malformed/unexpected model output must not crash
the caller.

**What needs to be done:**
- Add `ANTHROPIC_API_KEY` to `core/config.py` + `config.example.toml` (reused by
  translation in phase 0.8 — ARCHITECTURE §Configuration).
- `core/feedback.py` — `classify(text, title, top_node, api_key)` → a validated
  `{reaction: "like"|"dislike"|"new_topic", topic_hint: str|None}`; the prompt
  carries the card context, not just the raw text.
- Validate the model's structured reply; on a malformed/unexpected reply, raise
  a clear error rather than silently defaulting a reaction.
- All Anthropic HTTP is **mocked** in tests — never a live/paid call in CI.

**Dependencies:** None

**Expected result:**
`classify()` turns a card's text + context into a validated `{reaction,
topic_hint}`, given a (mocked) Haiku response.

**Acceptance criteria:**
- [ ] The classifier prompt includes the card's title and `top_node` alongside
      the user's text (not just the raw text).
- [ ] `reaction` is restricted to `like | dislike | new_topic`; `topic_hint` is
      present (name + keywords) only for `new_topic`.
- [ ] **Unit test:** a mocked Haiku reply → the validated `{reaction,
      topic_hint}`; a **malformed** reply (bad JSON / an unknown reaction) raises
      a clear error instead of crashing or silently defaulting — against mocks
      (no paid/network call).
- [ ] `ANTHROPIC_API_KEY` added to `config.example.toml`; `config.toml` stays
      gitignored.
- [ ] Ties to the phase DoD (feedback text → classified reaction).

### SROTAS-017 — Weight delta + events + `pending_topics.yaml` queue

**Description:**
The model-write and journal side. A classified `like`/`dislike` applies a
config-driven delta to the card's `top_node` weight via the existing
`core/model.set_weight` ruamel round-trip, clamped to `[0.05, 1.0]`. Every
feedback and every weight change is appended to `events.sqlite` (existing
`core/events.append_event`) carrying the user's original text and the item URL
— the trace runs feedback → node → item. `new_topic` never creates a node; it
lands in a new `memory/pending_topics.yaml` queue for manual confirmation
(ARCHITECTURE §Feedback, §Memory package).

**What needs to be done:**
- Add `feedback_like_delta` (+0.05) and `feedback_dislike_delta` (−0.07) to
  `core/config.py` + `config.example.toml`.
- `core/feedback.py` (or a sibling module) — `apply_reaction(reaction, node_id,
  item_url, text, model_path, events_db)`:
  - `like`/`dislike` → compute the new weight from the current one + the signed
    delta, clamp `[0.05, 1.0]`, write via `model.set_weight`; append a
    `feedback` event (kind=feedback, node_id, payload={text, url}) **and** a
    `weight_update` event (kind=weight_update, node_id, payload={delta,
    old_weight, new_weight}).
  - `new_topic` → append a `feedback` event (node_id=None, payload={text, url,
    topic_hint}); append the topic (id/label/keywords hint + first-seen item
    url) to `memory/pending_topics.yaml` (ruamel or plain YAML — no node is
    written to `model.yaml`); no weight change.
- `memory/pending_topics.yaml` starts as an empty list if absent; the file is
  tracked in git (ARCHITECTURE §Memory package — it is committed, unlike
  `events.sqlite`).

**Dependencies:** SROTAS-002, SROTAS-003

**Expected result:**
A classified reaction updates `model.yaml`'s weight (or queues a pending topic),
with a full audit trail in `events.sqlite`.

**Acceptance criteria:**
- [ ] `like`/`dislike` apply the configured delta to the card's `top_node` and
      clamp to `[0.05, 1.0]`.
- [ ] **Contract test:** each change writes a matching `events` row carrying the
      user's original text and the item URL (MISSION §Principles — auditable;
      ARCHITECTURE §Contracts, "model changes are traceable").
- [ ] `new_topic` goes to `pending_topics.yaml`, **never** creates or edits a
      `model.yaml` node.
- [ ] **Unit test:** like/dislike clamp at the 0.05/1.0 boundaries; `model.yaml`
      comments/formatting survive the write (ruamel round-trip); the events rows
      are present and correctly typed — against temp files (no paid/network
      call).
- [ ] Ties to the phase DoD (the weight changes; the event is logged).

### SROTAS-018 — `POST /feedback` wiring — classify → apply → re-score → reorder

**Description:**
Wires SROTAS-016 and SROTAS-017 into the live web app: the card's feedback field
(rendered inert since SROTAS-013) becomes a real `POST /feedback` — an HTMX
request from the card — that classifies the text, applies the model change, and
triggers a free re-score (cached embeddings) so the feed reorders immediately
(ARCHITECTURE §Feed, §Feedback).

**What needs to be done:**
- Enable the card's feedback `<form>` (SROTAS-013 left it `disabled`) to POST
  `{url, title, top_node, text}` to `/feedback` via HTMX.
- `web/app.py` — `POST /feedback`: loads the item, calls `feedback.classify`,
  then `feedback.apply_reaction`; on success, re-runs `core/scoring.score_items`
  (or the pipeline's scoring step) so `score`/`top_node` reflect the new weight;
  returns an HTMX-friendly response (e.g. re-rendered feed or a card
  acknowledgement).
- The route stays reachable **only from 127.0.0.1** (ARCHITECTURE §Feed — it
  spends money and mutates the model).

**Dependencies:** SROTAS-016, SROTAS-017, SROTAS-013

**Expected result:**
Typing a reaction on a card and submitting it changes the model, logs the event,
and the feed reorders on the next load — end to end, in the browser.

**Acceptance criteria:**
- [ ] `POST /feedback` classifies the text (mocked classifier in tests), applies
      the weight/pending-topic change, and re-scores.
- [ ] **Unit test (TestClient):** posting a `like` for a card raises its
      `top_node`'s weight and the item's `score` is updated on the next feed
      read; posting `new_topic` leaves `model.yaml` untouched and adds to
      `pending_topics.yaml` — against mocks (no paid/network call).
- [ ] The card's feedback field is no longer inert; it posts to `/feedback`.
- [ ] Ties to the phase DoD (feedback typed → classified → weight changes →
      event logged → feed reorders; pytest green).

## v0.5 scope notes

**Total effort:** ~2 weeks (3×M).
**Critical path:** SROTAS-016 / SROTAS-017 (parallel) → SROTAS-018 (also needs
SROTAS-013 from v0.4).
**Phase DoD (ROADMAP §0.5):** feedback typed → classified → the weight in
`model.yaml` changes → the event is logged → the feed reorders; pytest green.
**Contracts pinned this phase:** the **events row carries the original text +
item URL** for every feedback/weight_update change (SROTAS-017 contract test) —
already a stated contract (ARCHITECTURE §Contracts, "model changes are
traceable"); this phase is the first to exercise it end to end. No new schema
contracts — `events` stays the minimal 5-column shape from v0.1.
**Out of scope (ROADMAP §0.5):** auto-creating nodes from `new_topic`;
conversational feedback via Lili (stage 4). No stubs or config flags for them
(MISSION §Scope boundaries is binding).
**Mock note:** all paid APIs (Anthropic classification, Voyage embeddings) and
all collector HTTP are **mocked** in tests — never a paid or networked call in
CI. The real app, once run manually, does make a real (cheap) Haiku call per
feedback — that is the point of this phase, but it never happens in tests.
