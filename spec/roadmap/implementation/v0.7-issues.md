# v0.7 — GitHub Issues

Issues for phase **v0.7 — Full bootstrap** (version **v0 — Prototype**),
derived from the per-phase Tasks in [ROADMAP.md](../../ROADMAP.md) (§0.7) and
the contracts in [ARCHITECTURE.md](../../ARCHITECTURE.md) (§Bootstrap,
§Memory package, §Configuration). This file is scoped to a single phase; IDs
continue from the previous phase (SROTAS-021 → **SROTAS-022…027**).

This is the last v0 build phase: it replaces the one-off 14-node Lumi-facts
model with a **repeatable** bootstrap over four real personal sources — Lumi
conversations, a Claude export, browser history, and a Notion export — all
**snapshot-based, never live** (`bootstrap/snapshots/`, gitignored). Four
independent adapters normalize each source into plain text units; a chunked
Haiku pass extracts candidate topics; duplicates merge; the result is
`candidates.yaml` for **manual review** — no code path writes `model.yaml`
directly, matching the same hand-confirmation pattern as `pending_topics.yaml`
in phase 0.5.

## v0.7 — Full bootstrap

### SROTAS-022 — `bootstrap/lumi_snapshot.py` — Lumi `store.json` adapter

**Description:**
The primary source. Reads a hand-copied snapshot of `lumi/.lumi/store.json`
and extracts **`role=user` messages only** — the facts/summaries/thoughts
layers and the vectors file are not used here (ARCHITECTURE §Bootstrap).
Introduces the shared `bootstrap/units.py::TextUnit` (`source`, `text`) that
every adapter normalizes into.

**What needs to be done:**
- `bootstrap/units.py` — `TextUnit` (frozen dataclass: `source: str`,
  `text: str`).
- `bootstrap/lumi_snapshot.py` — `read_units(path) -> list[TextUnit]`: parses
  the snapshot JSON, filters to `role="user"` messages, maps each to a
  `TextUnit(source="lumi", text=...)`.
- A malformed/missing snapshot file raises a clear error rather than
  returning an empty result silently.

**Dependencies:** None

**Expected result:**
`read_units()` turns a Lumi `store.json` snapshot into a flat list of
`role=user` text units.

**Acceptance criteria:**
- [ ] Only `role="user"` messages are extracted; other roles are skipped.
- [ ] **Unit test:** a fixture snapshot (mixed roles) → the expected
      `role=user`-only `TextUnit` list, against a temp file (no network).
- [ ] A missing/malformed snapshot file raises a clear error.
- [ ] Ties to the phase DoD (a real source normalizes into text units).

### SROTAS-024 — `bootstrap/browser_history.py` — Chrome/Firefox history adapter

**Description:**
Reads a **copy** of the browser's history database (Chrome's `History` or
Firefox's `places.sqlite` — both are locked while the browser runs, so this
always operates on a snapshot copy) and extracts visited page titles +
domains as text units (ARCHITECTURE §Bootstrap).

**What needs to be done:**
- `bootstrap/browser_history.py` — `read_units(path) -> list[TextUnit]`:
  opens the SQLite file **read-only**; auto-detects the schema (Chrome's
  `urls` table vs. Firefox's `moz_places` table) by checking `sqlite_master`;
  reads `(url, title)` pairs and maps each to
  `TextUnit(source="browser_history", text=f"{title} — {domain}")`.
- Rows with an empty title are skipped (nothing to extract).
- An unrecognized schema (neither table present) raises a clear error.

**Dependencies:** None

**Expected result:**
`read_units()` turns a copy of Chrome or Firefox history into a flat list of
title/domain text units, regardless of which browser it came from.

**Acceptance criteria:**
- [ ] Both schemas (Chrome `urls`, Firefox `moz_places`) are recognized and
      produce the same `TextUnit` shape.
- [ ] **Unit test:** a fixture SQLite DB for each schema → the expected text
      units, against a temp file (no network).
- [ ] Rows with an empty title are skipped; an unrecognized schema raises a
      clear error.
- [ ] Ties to the phase DoD (a real source normalizes into text units).

### SROTAS-026 — Chunked LLM extraction + duplicate merge → `candidates.yaml`

**Description:**
The extraction core. Batches every source's `TextUnit`s into chunks, sends
each chunk to a Haiku-class call (same mockable-seam pattern as
`core/feedback.py`) that proposes candidate topics (id, label, keywords,
weight, a work-topic hint), then merges duplicate candidates across chunks
and sources before writing `candidates.yaml`. Deliberately simplified — no
daily windows, no segmentation, no citation validation (all stage 2, ROADMAP
§0.7 Out-of-scope).

**What needs to be done:**
- `bootstrap/extract.py` — `chunk_units(units, max_chars) -> list[list[TextUnit]]`:
  groups text units into bounded-size chunks (character budget, not token-
  exact — simple and sufficient here).
- `extract_candidates(chunk, api_key, *, call=None) -> list[dict]`: one
  Haiku-class call per chunk; the prompt asks for candidate topics as JSON
  (`id`, `label`, `keywords`, `weight` guess, `work: bool`); validates the
  reply the same way `core/feedback.classify` does — malformed output raises
  rather than silently defaulting.
- `merge_candidates(candidate_lists) -> list[dict]`: merges candidates whose
  `id` (or case-insensitive `label`) matches across chunks/sources, unioning
  their `keywords` and averaging `weight`.
- `write_candidates(candidates, path)` — writes `candidates.yaml` (ruamel,
  same flat-plus-metadata shape as the existing
  `spec/model-candidates.yaml`: `id`, `label`, `keywords`, `weight`, `work`).
- All Anthropic HTTP is **mocked** in tests — never a live/paid call in CI.

**Dependencies:** SROTAS-022, SROTAS-023, SROTAS-024, SROTAS-025

**Expected result:**
A mixed list of text units from all four sources becomes a deduplicated
`candidates.yaml`, ready for manual review.

**Acceptance criteria:**
- [ ] Chunking respects the character budget; every unit ends up in exactly
      one chunk.
- [ ] **Unit test:** a mocked Haiku reply per chunk → validated candidate
      dicts; a malformed reply raises a clear error (no paid/network call).
- [ ] **Unit test:** two chunks proposing the same topic (by id or label)
      merge into one candidate with the union of keywords.
- [ ] `candidates.yaml` is written in the same reviewable shape as
      `spec/model-candidates.yaml`.
- [ ] Ties to the phase DoD (extraction + merge produce reviewable
      candidates).

### SROTAS-027 — `bootstrap/bootstrap.py` — CLI orchestrator + bootstrap event

**Description:**
The entry point that closes the phase DoD: a CLI that takes each source's
snapshot path as an argument, runs every adapter present, feeds the combined
text units through SROTAS-026's extraction + merge, writes
`candidates.yaml`, and appends a `bootstrap` event to `events.sqlite`
recording which snapshot paths and dates were used (ARCHITECTURE §Bootstrap —
"the snapshot path is a CLI argument; its path and date are recorded in the
bootstrap event"). Enriching/replacing `memory/model.yaml` from
`candidates.yaml` stays a **manual** step — no code path does it
automatically, the same pattern as `pending_topics.yaml` → `model.yaml` in
phase 0.5.

**What needs to be done:**
- `bootstrap/bootstrap.py` — a CLI (`python -m bootstrap.bootstrap
  --lumi PATH --claude-export PATH --browser-history PATH --notion PATH`,
  each optional so a partial run over whatever snapshots exist is fine) that:
  - Runs the adapter for each provided path, collecting all `TextUnit`s.
  - Runs `extract.py`'s chunk → extract → merge → `write_candidates`.
  - Appends one `bootstrap` event (`core/events.append_event`) with a
    payload listing each source's snapshot path + today's date.
  - Prints a summary (sources used, text units read, candidates written).
- No step writes `memory/model.yaml`; the printed summary tells the human to
  review `candidates.yaml` and hand-move confirmed topics themselves.

**Dependencies:** SROTAS-026

**Expected result:**
One CLI command, run over whichever snapshots are available, produces a
reviewed-ready `candidates.yaml` and a traceable bootstrap event.

**Acceptance criteria:**
- [ ] Running with a subset of sources (e.g. only `--lumi`) works — absent
      sources are simply skipped, not required.
- [ ] **Integration test:** fixture snapshots for all four sources (mocked
      Haiku) → `candidates.yaml` is written and a `bootstrap` event is
      appended with the snapshot paths, against temp files (no paid/network
      call).
- [ ] `memory/model.yaml` is never written by this command.
- [ ] Ties to the phase DoD ("bootstrap runs over the real sources and
      yields a reviewed model of 10–15 nodes" — this issue produces the
      reviewable candidates; the 10–15-node model is the human's review
      outcome, not a code path).

## v0.7 scope notes

**Total effort:** ~3 weeks (3×S + 1×M + 1×L + 1×M).
**Critical path:** SROTAS-022/023/024/025 (parallel) → SROTAS-026 →
SROTAS-027.
**Phase DoD (ROADMAP §0.7):** bootstrap runs over the real sources and yields
a reviewed model of 10–15 nodes (closes the last overall-DoD item); pytest
green. *(The "reviewed model" step is the human's manual promotion of
`candidates.yaml` entries into `model.yaml` — this phase's code produces the
candidates; it never writes the model itself, matching every other
human-confirmation gate in this codebase.)*
**Contracts pinned this phase:** none new. `TextUnit` is new shared shape but
not one of ARCHITECTURE's pinned contracts (like `CollectSummary` in v0.6, it
is not schema-critical — freely adjustable without a spec amendment).
**Out of scope (ROADMAP §0.7):** daily windows, segmentation, citation
validation, returned/abandoned signals (all stage 2); auto-writing
`model.yaml` from candidates (MISSION §Scope boundaries — manual confirmation
only); wiring the topic blacklist into collector queries (ARCHITECTURE
mentions it, but the phase DoD only requires reviewed candidates — cutting
work topics happens at manual review, no code needed for that specifically).
**Mock note:** all Anthropic HTTP (extraction) is **mocked** in tests — never
a paid or networked call in CI. Every adapter is tested against **fixtures**
(no real personal snapshots needed to pass tests); a live run against real
snapshots is a separate, deliberate step the user takes after this phase
ships.
